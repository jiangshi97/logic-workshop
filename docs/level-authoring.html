2. 三分钟心智模型

关卡 = 一份 JSON 数据。判题 = 拿你声明的数学期望值（表达式 / 真值表 / 预填帧 / 编程用例）对比玩家搭的电路的实际输出。期望值完全不经过任何电路或仿真器——它是一个独立的小语言求值器，所以判题标准绝对客观。

装载链路（每一步都会在出错时给你带文件路径的报错）：

content/levels/*.json            基础 56 关（冻结，别动）
content/packs/<包名>/levels/*.json   你的新关卡（JSON 数据）
content/packs/<包名>/index.ts       包描述符：生成器/钩子/机器/章节的注册处
        │
        ▼  npm run regen:levels
src/levelData.generated.ts       关卡数据 + 源路径 + 包标记（提交入库）
src/levelPacks.generated.ts      包清单
        │
        ▼  应用启动 / npm test（compileCatalogue）
校验 + 编译成 Level 目录：id 平移、区间守卫、生成器展开、章节上界检查
        │
        ▼  运行时（App.tsx）
判题 / 解锁进度 / 钩子触发

最重要的两条习惯：① 改了任何关卡 JSON 后必须跑 npm run regen:levels，否则改动不会生效（生成文件提交入库是刻意的——Playwright 的转译器不支持 Vite 专有特性）；② 跑 npm test，它会把所有校验错误、编号冲突、快照变化报出来。

编号体系：基础目录（1–56）按 id 排序、id 即序号；关卡包里 JSON 的 id 只需在本包内唯一，全局 id = idBase + 包内 id。侧栏显示的「第 N 关」和解锁顺序一律按目录位置算——全局 id 921 的关卡显示为第 57 关。存档、判题、解锁用全局 id，所以 idBase 一旦定了就别改。

3. 快速上手：新增一个关卡包

目标：加一个新关卡，挂在第 8 章「指令集扩展」下，带一个开场钩子和一个用例生成器。总共五步：

第 1 步：建目录

content/packs/我的扩展/
  index.ts          # 包描述符（必需，唯一必需的文件）
  levels/001-xxx.json   # 关卡数据（注意是 levels，复数）

包的文件夹名就是包键，全局唯一；可以用小写字母、数字、连字符，也允许下划线、大写和中文（只要求 1–64 个字符、不含空格和斜杠）。

第 2 步：写 index.ts

import { range, type CaseGenerator, type HookContext, type LevelHook, type LevelPack } from 'logic-level-api';

const 开场白 = ({ level, showMessage }: HookContext) =>
  showMessage('欢迎', `「${level.title}」开始了！`);

const 我的用例: CaseGenerator = ({ localId }) => {
  if (localId !== 1) return [];        // 按包内编号分派（将来加第 2 关时用）
  return range(8).map(A => ({ A, B: 255 - A }));
};

export const pack: LevelPack = {
  key: '我的扩展',                     // 必须与文件夹同名
  idBase: 1000,                        // 全局 id = 1000 + JSON id，选远离 56 的固定值，永不改动
  chapters: ['指令集扩展'],             // 可选：追加章节（第 8 章）
  caseGenerators: new Map([['my-cases', 我的用例]]),
  hooks: new Map([['开场白', 开场白]]),  // Map 键 = JSON 引用的后半段；TS 函数名随意
};

第 3 步：写 levels/001-xxx.json

抄第 4 节的字段参考，或直接抄 content/packs/useful-computer/levels/001-alu-plus.json 改。

第 4 步：生成 + 测试

npm run regen:levels    # JSON 进生成文件
npm test                # 校验 + 快照（新关卡会让快照失败，见第 13 节）

第 5 步：试玩

npm run dev

如果要让浏览器端到端测试（Playwright）也能自动通关你的关卡，还要在 tests/fixtures.ts 加参考电路（第 14 节）。

4. 关卡 JSON 完全参考

字段类型必填规则
id正整数必填基础目录：全局唯一；关卡包：仅本包内唯一，从 1 编起、允许跳号。全局 id = idBase + id。
title / captionstring必填非空。名称与副标题。
goal / formulastring必填非空。任务正文与数学公式。
chapter正整数必填≥1。上界不是写死的：装载时按「基础 7 章 + 各包 chapters 追加的章节数」动态检查，超出会报错并告诉你总数。
inputs / outputs[端口名, 位宽][]必填端口名必须是合法标识符 [A-Za-z_][A-Za-z0-9_]*（这是期望值表达式语言的限制，见第 6 节），不能用保留字 div/mod；位宽 1–32；输入与输出端口名不能重名。
allowed门型数组可选本关可用的门型。省略时：id ≤ 20 的关卡按解锁表推导（NAND@2、NOT@4、AND@5、OR@6、XOR@7、XNOR@8、SPLIT/JOIN@11、CONST@19），其余关卡取全部门型。
hintsstring[3]必填恰好三条递进提示，一条都不能少。
rewardNamestring可选通关后把整关电路打包成组件时的默认名。
defaultProgramnumber[]可选ROM 初始指令字，最多 256 个 16 位字（0–65535）。
hooks对象可选必须写在 JSON 顶层（放进 combinational 里会被静默忽略！）。格式 { 事件名: "包键/钩子名" }，见第 11 节。
combinational / sequential / program对象三选一判题模式段，必须恰好提供一个，给了两个或一个都不给都会报错。

5. 判题模式一：combinational

组合逻辑关。期望值来源三选一/二选一：

5.1 expect 表达式（首选）

"combinational": {
  "expect": {
    "Diff": "(A - B) mod 16",
    "Borrow": "A < B"
  }
}

每个输出端口一条表达式，必须恰好覆盖每个输出（多写、少写都报错）。语法见第 6 节。

5.2 truthTable 真值表（小输入空间可读写法）

"combinational": {
  "truthTable": [
    { "inputs": { "A": 0, "B": 0 }, "outputs": { "Y": 1 } },
    { "inputs": { "A": 1, "B": 0 }, "outputs": { "Y": 0 } }
  ]
}

expect 与 truthTable 二选一。每行 inputs 必须覆盖全部输入端口、outputs 必须覆盖全部输出端口，且值不得超出端口位宽。

5.3 cases 公开测试集

省略 cases 时判题穷举全部输入组合（2^总位数 种）。总位数一大就不可行——8+8+4 = 20 位就是 100 万次仿真。这时声明公开用例集：

// 写法一：手写数组（每项必须覆盖【全部】输入端口，值不超位宽）
"cases": [ { "A": 0, "B": 1, "Sub": 1 } ]

// 写法二：生成器引用（推荐，数据在 TS 里造）
"cases": { "generator": "我的扩展/my-cases" }

真实踩坑：引用了基础目录的 "generator": "alu-cases" 但你的关卡有六种运算？基础生成器只生成 Op 0–3 的用例，你的 Op=4/5 分支永远不会被判题，一个没实现它们的电路也能通关。基础生成器是冻结的（老关卡判题标准不能变），所以运算集不同就必须在自己包里写生成器（第 10 节）。

6. 期望值表达式语言

纯整数运算的安全小语言（src/levelExpr.ts），无函数调用、无属性访问、因此没有注入面。优先级与 C 一致，从低到高：

类别运算符说明
三目a ? b : c可链式；复杂译码逻辑靠它
位或|
位异或^
位与&
相等= !=注意是 = 不是 ==；结果为 1 或 0
关系< <= > >=结果为 1 或 0
移位<< >>
加减+ -
乘除* div moddiv/mod 是保留字（不能作端口名）
一元- ~~ 按位取反
原子数字、端口名、括号数字支持十进制与 0x 十六进制
  • div 是向下取整除法；mod 是与除数同号的数学取模——所以 (A - B) mod 16 在 A<B 时直接得到补码结果，不用自己加 16。
  • 求值结果自动按输出端口位宽取模（接 1 位输出时 ~(A & B) 自动变成 0/1）——但注意只在输出端口处取模：表达式中间值保持原始整数（可为负）。真实案例：~A 对 A=255 得 -256，输出到 8 位端口显示 0，但写进 Z 的比较式 (~A) = 0 用的是原始值 −256，永远不成立。
  • 除零在求值时抛错；引用未声明的端口名在编译期报错（错误信息带位置）。
  • 端口名必须匹配 [A-Za-z_][A-Za-z0-9_]*——这就是第 4 节端口命名限制的来历。

7. 判题模式二：sequential

时序关。期望值预填在帧里，逐场景逐步骤回放。

7.1 手写场景（步数可控时用）

"sequential": {
  "scenarios": [
    {
      "label": "写入与保持",
      "steps": [
        { "inputs": { "D": 1 }, "tick": false, "expected": { "Q": 0 } },
        { "inputs": { "D": 1 }, "expected": { "Q": 1 } },
        { "inputs": { "D": 0 }, "tick": false, "expected": { "Q": 1 } }
      ]
    }
  ]
}
  • 每步 inputs 可省略端口（缺省 0）；tick 缺省 true（推进一个时钟沿），false 表示只改输入不出沿。
  • expected 必须覆盖全部输出端口，值不超位宽。
  • 场景可带 program（最多 256 个 16 位指令字）为该场景预置 ROM——取指/整机关靠它逐场景换程序。
  • 建议先用参考电路在工坊里把期望值跑出来再誊写。

7.2 生成器引用（海量穷举帧时用）

"sequential": { "generator": "我的扩展/my-scenarios" }

手写与生成器二选一。生成数据与手写数据走完全相同的校验。

8. 判题模式三：program

编程关：在真实门级 CPU 上执行玩家写的 ROM，期望值只来自你声明的数学用例。

"program": {
  "machine": "computer-44",              // 可选：绑定的计算机注册表键；缺省取第一台
  "cases": [
    {
      "label": "RAM[240]=7",
      "memory": { "240": 7 },             // 地址（"0"–"255" 字符串键）→ 初始字节
      "expectedOutput": [21],             // 期望的完整 OUT 序列（0–255 字节）
      "maxCycles": 400,                   // 周期预算，1–100000
      "expectedMemory": { "100": 21 }     // 可选：期望的最终内存
    }
  ],
  "referenceSource": "MOVI A, 3\nOUT 0\nHLT"   // 参考汇编源（≤32000 字符）
}
  • cases 不能为空；每个用例必须有 label。
  • machine 键规则：1–64 字符，不含空格与斜杠。

9. 关卡包 index.ts 完全参考

一个包 = content/packs/<包名>/ 一个目录。类型 LevelPack 从 'logic-level-api' 导入（npm workspace 包，直接按名字 import，不用相对路径）：

import { type LevelPack } from 'logic-level-api';

export const pack: LevelPack = {
  key: '我的扩展',          // 必须 === 文件夹名
  idBase: 1000,             // 正整数，一次性决定，永不改动
  chapters: ['指令集扩展'],  // 可选：追加章节标题
  scenarioGenerators: new Map(),  // 可选：场景生成器注册表
  caseGenerators: new Map(),      // 可选：用例生成器注册表
  machines: [],                   // 可选：新计算机描述符
  hooks: new Map(),               // 可选：钩子注册表
};
字段规则
key= 文件夹名。1–64 字符，不含空格与斜杠——下划线、大写、中文都可以。JSON 里的引用以它做命名空间前缀。
idBase正整数。包内全部关卡的全局 id 必须 > 基础目录最大关卡号（56）且与其他包的区间不相交——装载守卫会检查并报出冲突双方。相邻包留足间隔（如 1000 / 2000）。
chapters追加的章节标题，编号接在基础 7 章之后，按包的装载顺序排。
scenarioGenerators / caseGeneratorsMap<名字, 函数>，名字只需包内唯一。见第 10 节。
machinesMachineDescriptor[]，sourceLevel 写包内编号，装载时自动翻译成全局 id。见第 12 节。
hooksMap<名字, (ctx) => void>。见第 11 节。

包规则（防装载循环，违反会炸得很难看）

  • index.ts 顶层只组装描述符，不要在模块顶层调用游戏运行时函数——模块求值期关卡目录还没就绪。函数体里（回调里）随便调。
  • 生成器与钩子不得 import levels 目录。
  • 对 src/machines.ts 只做 import type（防运行时循环依赖）；其余核心模块随意。
  • 包内自定义组件键避开基础目录的 architecture-* 前缀。

10. 生成器：用 TypeScript 造判题数据

生成器 = 一个普通函数，在目录装载时（应用/测试每次启动）执行一次，返回值经与手写数据完全相同的校验后物化缓存，判题时反复使用。

10.1 类型与上下文

import { rng, range, type CaseGenerator, type ScenarioGenerator } from 'logic-level-api';

// 用例生成器：返回一组完整输入赋值（组合关 cases）
const myCases: CaseGenerator = ({ id, pack, localId, inputPorts, outputPorts }) => [ ... ];

// 场景生成器：返回帧时间线（时序关 scenarios）
const myScenarios: ScenarioGenerator = ({ inputPorts }) => [ ... ];

上下文 GeneratorContext：

字段含义
id全局 id（idBase 平移后）。基础生成器（temporal 等）按它分派老关卡。
localId包内编号（JSON 里的 id）。包生成器应该按它分派——它不随 idBase 变化。
pack所属包键（包生成器才有）。
inputPorts / outputPorts{ id, label, bits }[]，可直接推导缺省值或位宽。

10.2 注册与引用（命名空间规则）

  • 注册：包 index.ts 里 caseGenerators: new Map([['my-cases', fn]])。
  • 引用：JSON 写 "generator": "我的扩展/my-cases"（带包键前缀）→ 查你的包。
  • 裸名（如 "alu-cases"）→ 查基础目录 src/levelGenerators.ts 的注册表（temporal / architecture / alu-cases / controller-cases）。老关卡引用零迁移。
  • 查不到的名字在装载时报 未知的生成器"xxx"。

10.3 必须纯且确定

生成器每次启动都会重新执行，且测试快照会把判题数据的条数与 sha1 摘要钉死。不要用 Math.random()——用包里提供的确定性随机：

import { rng, range } from 'logic-level-api';
const random = rng(42);          // mulberry32，同种子永远同一序列
range(256)                        // → [0, 1, …, 255]

10.4 用例设计范式（抄得走的经验）

总位数大时不可能穷举，标准折中是「全枚举一个操作数 × 边界采样另一个 × 控制信号全覆盖」。以六运算 ALU 为例（即 useful-computer 包的 alu6-cases）：

const alu6CaseList: CaseGenerator = ({ localId }) => {
  if (localId !== 1) return [];
  const cases = [];
  for (const A of range(256)) {                       // 操作数一：全枚举
    const partners = new Set([0, 1, 127, 128, 254, 255, A, 255 - A, (A * 73) & 255]);
    // ↑ 边界伙伴集：0/1 零与最小增量、127/128 补码分界、254/255 溢出、
    //   A 自身（测零标志）、255-A 恰不进位、A·73 伪随机普通值
    for (const B of partners) for (const op of range(6)) cases.push({ A, B, Op: op }); // 控制全覆盖
  }
  for (const [A, B, Op] of [[0, 0, 6], [255, 1, 15], [128, 128, 9]] as const)
    cases.push({ A, B, Op });                         // 非法 Op 定点抽检
  return cases;
};

11. 钩子：事件驱动的特殊行为

钩子是普通 TypeScript 函数，在游戏事件发生时被调用，只能通过上下文 API 产生可见效果。声明在关卡 JSON 顶层：

"hooks": { "onEnter": "我的扩展/开场白" }

引用命名规则（已放宽）：两段各 1–64 个字符、不含空格与斜杠——下划线、大写、中文都可以。TS 侧 Map 键与 JSON 引用的后半段一致即可，函数名随意。

11.1 九个事件

事件次数触发时机带 test
onEnter一次性首次进入该关—
onEveryEnter每次每次进入该关—
onFirstHint一次性玩家展开第一条提示—
onAllHints一次性三条提示全部展开—
onFirstFail一次性该关第一次判题失败✓
onFirstClear一次性该关第一次通过判题（「第一次通关后执行特殊行为」就是它）✓
onEveryTest每次每次判题（通过/失败都算）✓
onFirstPackage一次性首次把整关电路打包成组件—
onFirstProgramApply一次性编程关首次应用汇编程序—

一次性事件的触发记录随存档持久化（firedHooks），导入/刷新不会重放；周期性事件不持久化。钩子未注册或执行抛错都只弹 toast，不会弄崩游戏。

11.2 HookContext 完整 API

const 我的钩子 = ({ level, event, notify, showMessage, progress, catalog, store, draft, test }: HookContext) => { … };
成员类型 / 签名说明
levelLevel触发事件的关卡（编译后的完整数据）。
event事件名字符串同一个函数注册到多个事件时用来分派。
notify(text)(string) => void右下角 toast（4.5 秒自动消失）。
showMessage(title, body)(string, string) => void模态消息框，玩家点「知道了」关闭。
progress只读进度查询done() 已通关数；total() 目录总数；isCleared(id?) / isUnlocked(id?) / displayNumber(id?)（侧栏「第 N 关」的 N）/ nextLevelId(id?)（末关返回 undefined）。不带参数时作用于触发钩子的这一关。
catalog只读目录视图get(全局id)、all()、chapters()。
store本关私有键值存储见下。
draft{ nodes, wires }触发时刻本关草稿电路的节点/连线计数（只读统计）。
test{ passed, failure?: { inputs, mismatches } }仅判题类事件携带：失败时的触发输入与不匹配的输出端口名。

11.3 store：本关私有持久化

store.set('clearCount', 1);            // 写（键：1–64 字符不含空格；值必须可 JSON 序列化）
store.get<number>('clearCount');       // 读（不存在返回 undefined）
store.delete('clearCount');
store.keys();
  • 随存档（v7 的 packState 字段）持久化，导入/刷新后仍在；按关卡隔离，别的关卡读不到。
  • 限额（防存档爆炸，是刻意保留的硬限制）：单个值 ≤ 64 KiB；每关合计 ≤ 256 KiB。超了在 set 时抛错。
  • 写后读语义：同一次调用里先 set 再 get 读到的是旧值（写入走 React 状态提交）。

11.4 完整示例（有状态教练）

import type { HookContext, LevelHook } from 'logic-level-api';

const coach: LevelHook = ({ notify, store, test }: HookContext) => {
  if (test?.passed) return;
  const fails = (store.get<number>('failCount') ?? 0) + 1;
  store.set('failCount', fails);
  if (fails >= 2) notify(`已连续未通过 ${fails} 次，试试从最高位进位开始检查。`);
};

14. e2e 参考电路（fixtures.ts）

真实踩坑：Playwright 的验收测试会遍历目录里的每一关自动通关。新关卡没有参考电路时直接报 No reference circuit for lesson 921。加完关卡必须去 tests/fixtures.ts 的 referenceCircuit() switch 里加一个 case。

参考电路用文件内私有的 Builder DSL 搭（全部是 1 位门，总线靠 SPLIT/JOIN）：

API说明
b.input('A')取输入端口引脚。
b.gate('AND', a, b)1 位门（b 可省略，如 NOT）。
b.constant(0, 8)常量（默认 1 位）。
b.split(pin, 4)拆位 → 引脚数组，下标 0 是最低位。
b.join(pins)合并为总线。
b.mux(a, b, s)s=1 选 b。内部是 NOT+AND+OR 的 1 位组合——总线选择要 split 后逐位 mux 再 join（case 921 的树形选择就是范例）。
b.fullAdder(a,b,cin) / b.ripple(a[], b[], cin)加法器；ripple 返回 { sum: 总线引脚, cout }。
b.output(pin, 'Y')接输出端口。

分派规则：编程关 → 编程参考；chapter 6 → 架构参考；chapter 5 且 id > 20 → 时序参考；其余（包括你的新包关卡）走 switch 按全局 id 加 case。多路选择用「16 槽树形 mux、非法槽位接常量 0」的范式（抄 case 921）。

16. 保留下来的限制及原因

这些限制是刻意设计的，放开会破坏教学语义或存档安全：

限制为什么保留
包关卡全局 id 必须 > 基础最大关卡号、各包区间不相交、idBase 发布后不可改保住「id 序 == 目录序」不变式：教学组件解锁、进度、存档里的十几处 id 比较都依赖它。
端口名必须是 ASCII 标识符、不能用 div/mod端口名直接进入期望值表达式语言（第 6 节），语言词法就这么大。
hints 恰好三条三层递进提示是玩法设计（也绑定 onFirstHint/onAllHints 事件语义）。
位宽 1–32、maxCycles 1–100000、ROM ≤ 256 字、referenceSource ≤ 32000 字符仿真与存档的工程上限。
store 值 ≤ 64 KiB / 每关 ≤ 256 KiB、值必须可 JSON 序列化存档进 localStorage，防膨胀损坏。
基础 56 关判题数据冻结（快照钉死）已发布关卡的通关标准不能悄悄变化。

已放宽的命名限制（2026-10）：钩子引用、包键、机器键、store 键现在只要求「不含空白（钩子引用另不含斜杠）、长度 1–64」——下划线、大写字母、中文都可以用。章节号上限改为随包声明动态计算。如果你又被某条规则拦住，先来这张表和第 15 节找原因。
